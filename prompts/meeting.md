# 회의록 (doc_type=meeting)

회의 트랜스크립트를 정리해 **결정·액션 중심**의 IT 업무 회의록을 작성하세요.
참석하지 않은 사람이 읽어도 논의 맥락과 결정 근거가 그대로 잡히도록, 실무에서 바로 쓸 수 있는 수준으로 작성합니다.

`_base.md` 의 **밀도 규약**(요약이 아니라 재구성)과 **서식 규약**(가독성)이 이 문서에도 그대로 적용됩니다.

---

## STT 노이즈 보정

본 시스템은 Whisper 기반 STT를 사용합니다. 한국어 외래어·기술 용어가 발음 유사 단어로 오인식되는 경우가 잦으므로, **본문 작성 직후 `_typo_gate.md` 의 검토 항목(§1~§10) + 게이트 체크리스트를 반드시 통과**시켜야 합니다 (조사·받침·영어 음독·파편 단어·문맥 + 사내 고유명사 / LLM·AI 모델 / 관용구 / 영문 약어 사전 + 의심 표기 마킹 + 민감정보 마스킹).

회의록 작성 단계에서 본문에 들어가는 인용·논의 요약·결정사항 모두 동일 사전 적용 대상입니다. 로더가 자동으로 `_typo_gate.md` 를 본 프롬프트 뒤에 append 합니다.

---

## 참석자 식별

**`_people.md` 의 팀 참석자 사전이 인명의 정답입니다.** 로더가 자동으로 본 프롬프트 앞에 붙입니다.

- 트랜스크립트의 이름·호칭이 사전의 인물과 발음이 비슷하면 **사전의 실명으로 복원**하세요 (STT는 한국어 인명을 거의 반드시 틀립니다).
- 개요의 참석자, 논의 요약의 발화 주체, **액션 아이템의 담당자를 모두 실명으로** 씁니다.
- 사전에 없는 인물(타 팀·고객사·외부인)은 들린 대로 쓰되, 확신이 없으면 `(불명)`.
- 화자 분리가 없는 경우 "발언자 다수" + 식별된 실명 나열.

## 출력 구조

### 1. 회의 제목
`title` 힌트 우선, 없으면 본문 첫 발언·주제에서 추정.

### 2. 개요 (표)

| 항목 | 내용 |
|---|---|
| 일시 | 트랜스크립트 메타·언급에서 추정; 불확실하면 "(추정)" 표기 |
| 소요시간 | 타임스탬프로 추정 가능하면 표기 |
| 참석자 | 위 참석자 식별 규칙 적용 |
| 회의 유형 | 정기회의 / 기획회의 / 의사결정 / 문제해결 / 브리핑 중 하나 |
| 회의 목적 | 이 회의를 연 이유를 1~2문장으로 (트랜스크립트 도입부·배경에서 추출) |
| 한 줄 결론 | 이 회의에서 결국 무엇이 정해졌는가 (1문장) |

### 3. 핵심 결정사항

**합의·결정된 사항만.** 논의 중인 것은 §6 미결로 보냅니다.

각 결정은 아래 3단으로 씁니다. 결정만 남기고 근거를 지우면 나중에 왜 그렇게 했는지 아무도 모릅니다.

```markdown
- **{결정 내용}**
  - **근거**: 왜 이렇게 정했는가 (회의에서 나온 이유·데이터·제약)
  - **영향**: 무엇이 바뀌는가 / 누가 무엇을 해야 하는가 (해당 없으면 생략)
```

- 대안이 검토되다 기각됐다면 "무엇을 왜 기각했는지"를 근거에 함께 남기세요.
- 조건부 결정("~하면 재검토")은 그 조건까지 적으세요.

### 4. 요청 / 요구사항

누가 무엇을 요청하거나 요구했는지를 정리합니다.
- 클라이언트·이해관계자의 요구사항, 팀 간 요청사항, 조건·제약 사항 등
- 공식 결정으로 이어지지 않은 것도 포함
- 형식: `[요청자/출처] → 내용` (불릿). 요청 배경이 있으면 한 줄 덧붙이세요.
- 해당 사항 없으면 "없음" 한 줄

### 5. 액션 아이템 (표)

| 담당자 | 작업 내용 | 마감 | 우선순위 |
|---|---|---|---|
| 이름/직책 | 구체적인 할 일 (무엇을 어디까지) | YYYY-MM-DD (불명이면 "(미정)") | 상 / 중 / 하 |

- 담당자가 불명이면 "담당자 미정" 기재
- "작업 내용"은 동사로 끝나는 실행 가능한 문장으로. "~ 검토"보다 "~ 를 확인해 월요일 회의에 안 가져오기"처럼 완료 판정이 가능하게.
- 마감이 언급되지 않았으면 추정하지 말고 "(미정)"

### 6. 미결 사항 & 리스크

결론 나지 않은 사항, 추가 확인이 필요한 항목, 잠재 리스크.
각 항목은 **무엇이 미결인지 + 왜 못 정했는지(대립 지점) + 무엇이 정해져야 풀리는지** 를 담아 1~3문장으로.
없으면 "특이사항 없음" 한 줄.

### 7. 논의 요약 (본문 — 가장 두꺼워야 하는 섹션)

**커버리지 원칙:**
- 회의에서 다룬 **모든 기능·이슈·작업·현황 항목을 빠짐없이** 토픽으로 커버하세요.
- 현황 보고(완료된 것, 진행 중인 것)도 논의 요약에 포함하는 것이 올바릅니다.
- 누락 점검: 타임스탬프 10분 이상 구간 중 어느 토픽에도 안 잡힌 곳이 있으면 빠뜨린 것입니다.
- **토픽 개수 기준: 회의 1시간당 4~7개.** 2시간 회의면 8~14개. 억지로 쪼개지 말고 회의의 자연스러운 주제 단위로 나누세요.

**토픽 템플릿** — 각 토픽은 `### ` 헤딩으로 시작합니다.

```markdown
### {토픽 제목}

**{한 줄 리드 — 이 토픽의 결론·요지}**

{쟁점과 배경: 왜 이 얘기가 나왔는가. 1~3문장}

{논의 전개: 누가 무엇을 주장했고 근거가 무엇이었는가. 반론이 있었으면 그 논거까지.
수치·서버명·제품명·기한은 원문 그대로 보존. 여러 단락으로 나눠도 좋습니다.}

{결론: 무엇으로 정리됐는가. 결론이 안 났으면 "무엇이 걸려서 못 정했는지"를 명시하고 §6 미결과 연결}
```

**분량:**
- 실질적 논의(수치·결정·이견·기술 설명)가 있었던 토픽은 **최소 5~8문장**, 논쟁이 길었던 토픽은 여러 단락으로.
- 한두 마디로 지나간 항목은 짧게 써도 되지만, **생략은 하지 마세요.**
- 사담·반복 확인·시연 조작 대화만 생략합니다.
- 회의가 길다는 이유로 압축하지 마세요. 길면 긴 만큼 씁니다.

### 8. 다음 단계
- 다음 회의 일정 (언급된 경우)
- 주요 마일스톤·보고 일정 (트랜스크립트에서 언급된 것만)
- 날짜가 있으면 `YYYY-MM-DD(요일) — 내용` 형식으로 시간순 정렬
- 없으면 섹션 생략

### 9. 원문 인용
`[HH:MM:SS] "발언 내용"` — 회의 1시간당 3~5건 기준. 결정·전환점이 된 발언, 대립이 드러난 발언 위주.
(1시간 이하: 최대 5건 / 2시간: 최대 10건 / 3시간 이상: 최대 15건)

인용으로 본문을 대신하지 마세요. 본문이 먼저입니다.

## Notion DB 속성 매핑 (database 타겟일 때, 스키마 확인 후 적용)

| 가능한 컬럼 | 채우는 값 |
|---|---|
| 회의 제목 / Title | 위 1의 제목 |
| 날짜 / Date | 잡 생성일 (오디오 녹음일 추정 못하면) |
| 참석자 | 위 개요의 참석자 텍스트 |
| 회의 유형 (multi_select) | 위 개요의 회의 유형 (스키마에 정의된 옵션 중에서만 선택) |
| 유관 부서 (multi_select) | 본문 키워드로 추정한 부서 (옵션 중에서만) |
| 주요 결정 & 액션 아이템 | 3+4+5 요약 (1~3줄) |

## 금지

- 트랜스크립트에 없는 사실 추가 (할루시네이션) 금지. 모르면 "(불명)"으로 표시
- 욕설·민감정보는 `[...]` 로 마스킹
- 인용 발언은 한 줄 60자 이내, 길면 "..." 로 발췌
- 결론 안 난 사안을 결정사항으로 기재 금지
- 논의된 항목을 논의 요약에서 생략 금지
- 결정의 근거·반론을 지우고 결론만 남기는 것 금지
