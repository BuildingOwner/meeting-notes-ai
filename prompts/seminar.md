# 세미나 / 발표 노트 (doc_type=seminar)

발표·세미나 트랜스크립트를 정리해 **내용 이해 + 실무 적용**이 가능한 노트를 작성하세요.
발표를 못 들은 사람이 이 노트만 읽고도 발표자의 논지와 근거를 따라갈 수 있어야 합니다.
"이 발표에서 무엇을 얻어야 하는가"를 중심으로 구성하되, **줄이는 것이 목적이 아닙니다.**

`_base.md` 의 **밀도 규약**(요약이 아니라 재구성)과 **서식 규약**(가독성)이 이 문서에도 그대로 적용됩니다.

---

## STT 노이즈 보정

본 시스템은 Whisper 기반 STT를 사용합니다. 한국어 외래어·기술 용어가 발음 유사 단어로 오인식되는 경우가 잦으므로, **본문 작성 직후 `_typo_gate.md` 의 검토 항목(§1~§10) + 게이트 체크리스트를 반드시 통과**시켜야 합니다. 발표 자료·제품명·논문명·수치는 특히 오인식이 잦으니 문맥으로 복원하고, 확신이 없으면 `(추정)` 을 붙이세요.

**인명은 `_people.md` 의 팀 참석자 사전이 정답입니다.** 발표자·질문자가 사전의 인물과 발음이 비슷하면 사전의 실명으로 복원하세요. 사전에 없는 외부 발표자는 들린 대로 쓰되 확신이 없으면 `(불명)`.

## 출력 구조

### 1. 세미나 제목
`title` 힌트 우선, 없으면 발표 첫 단락에서 추정.

### 2. 개요 (표)

| 항목 | 내용 |
|---|---|
| 일시 | 트랜스크립트 메타·언급에서 추정; 불확실하면 "(추정)" 표기 |
| 소요시간 | 타임스탬프로 추정 가능하면 표기 |
| 발표자 | 트랜스크립트 단서·메타에서 추정 (불명이면 "(불명)") |
| 청중 규모 | 소규모 인터랙티브 / 대규모 강당 / 워크숍 등 톤으로 분류 |
| 주제 | 한 줄 요약 |
| 발표 배경 | 왜 이 발표가 이루어졌는지, 어떤 문제의식에서 출발했는지 1~2문장 |
| 한 줄 결론 | 발표자가 결국 무엇을 주장했는가 (1문장) |

### 3. 핵심 인사이트 (Takeaways)

이 발표에서 반드시 기억해야 할 **"So What"** 3~5개.
- 단순 정보 나열이 아닌, 발표자의 핵심 **주장·결론·관점**
- 각 인사이트는 `**주장** — 근거 한 줄` 형태로. 주장만 있고 근거가 없으면 인사이트가 아니라 구호입니다.
- 실무나 의사결정에 적용 가능한 형태로 작성

### 4. 주요 내용 (본문 — 가장 두꺼워야 하는 섹션)

발표 본론을 흐름 순서대로 `### ` 헤딩으로 구분합니다.
**섹션 개수 기준: 발표 30분당 3~5개, 1시간이면 5~8개.** 발표자가 만든 자연스러운 흐름 단위로 나누세요.

**섹션 템플릿:**

```markdown
### {섹션 제목}

**{한 줄 리드 — 이 대목에서 발표자가 말한 결론}**

{설명: 발표자의 논지를 학습자가 읽기 좋게 재구성. 추임새·반복 제거, 논리 순서 정돈.
발표자가 든 비유·은유는 보존. 5~10문장, 필요하면 여러 단락.}

{근거·수치·사례: 발표자가 제시한 데이터·벤치마크·회사 사례·데모를 원문 값 그대로.
표·코드·의사코드로 보여준 것은 같은 형태로 재현.}

{한계·전제: 발표자가 스스로 밝힌 제약이나 "이건 우리 환경 얘기"류 단서가 있으면 반드시 남길 것}
```

**분량:**
- 실질 내용(수치·사례·기술 설명)이 있었던 섹션은 **최소 5~8문장.**
- 발표자가 짧게 지나간 대목은 짧게 쓰되 **생략하지는 마세요.**
- 사담·행사 안내·장비 점검 멘트만 생략합니다.

### 5. 개념·용어 정리 (표)

새로운 개념이나 발표자가 정의한 용어. 없으면 섹션 생략.

| 용어 | 정의 | 발표자 맥락 |
|---|---|---|
| 용어명 (원어 병기) | 발표자가 제시한 정의 (임의 수정 금지) | 이 발표에서 어떤 문맥으로 사용됐는지 |

### 6. Q&A 정리

트랜스크립트에서 식별된 질문·응답만 정리. 없으면 섹션 생략.
Q&A는 발표에서 가장 밀도 높은 대목인 경우가 많습니다. **한 줄로 줄이지 마세요.**

```markdown
**Q (HH:MM:SS)** — (질문자 불명이면 "청중") {질문 요지}
> 질문 배경·의도가 드러나면 한 줄 덧붙임

**A** — {답변 핵심 결론}
{답변 근거·부연 3~6문장. 발표자가 답을 못 하거나 "확인해보겠다"로 넘긴 것도 그대로 기록}
```

### 7. 후속 과제 & 참고 자료
- 발표자가 언급한 follow-up 액션, 추천 자료(책·논문·링크), 참고문헌
- 청중에게 요청된 과제나 숙제
- 없으면 섹션 생략

### 8. 원문 인용
`[HH:MM:SS] "발언 내용"` — 발표 1시간당 3~5건. 핵심 통찰·주장이 드러난 문장 위주.
인용으로 본문을 대신하지 마세요. 본문이 먼저입니다.

## Notion DB 속성 매핑 (database 타겟일 때, 스키마 확인 후 적용)

| 가능한 컬럼 | 채우는 값 |
|---|---|
| 회의 제목 / Title | 위 1의 제목 |
| 날짜 / Date | 잡 생성일 |
| 회의 유형 (multi_select) | `세미나` 옵션 (스키마에 있으면) |
| 참석자 | 발표자 + 청중 규모 (예: "발표자: 김OO, 청중: ~20명") |
| 주요 결정 & 액션 아이템 | 위 7의 후속 과제 (있을 때만) |

## 금지

- 발표자가 말하지 않은 내용 추가 금지
- 청중 질문을 발표자 발언으로 혼동하지 말 것 — 화자 단서가 약하면 "Q: (청중)" 으로 표기
- 핵심 인사이트를 단순 정보 목록으로 채우지 말 것 — 발표자의 "주장"과 그 근거를 담아야 함
- 발표자가 든 수치·사례를 지우고 결론만 남기지 말 것. 근거가 빠지면 노트의 가치가 사라집니다
- 섹션 본문을 1~2문장으로 때우지 말 것 (발화량 자체가 적었던 대목은 그 사실을 한 줄로 명시)
